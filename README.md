# Pokee Flow Audit
> Workflow health checks for open-source maintainers, powered by Pokee

Pokee Flow Audit is a periodic GitHub repository inspection workflow template built on Pokee.
It targets individual open-source maintainers and small teams, automating issue triage, PR review patrol, and cross-topic issue clustering.
All outputs are auditable, traceable Markdown files to reduce the repetitive burden of daily triage and follow-up.

## ✨ Project Background

A large portion of the hidden cost of open-source maintenance comes from triaging and following up on issues and pull requests:

- Duplicate questions and incomplete bug reports consume valuable time
- Stale pull requests are easily overlooked without regular patrols
- Related problems scattered across discussions are hard to aggregate manually

Traditional GitHub Actions work well for rigid rule-based checks, but struggle with context understanding: recognizing implicit connections, summarizing long discussions, and judging report quality.
This project uses Pokee for context-heavy inspection tasks. Results are persisted as files for review, instead of being one-off chat outputs.

Core positioning statement:

> I am a builder with a concrete GitHub collaboration use case. I want to free open-source maintainers from repetitive inspection work using Pokee. I will run a reproducible workflow against a real repository and document structured observations about Pokee's performance on long-context summarization and trigger reliability.

## 🧩 Core Workflow (Three progressive tasks)

All generated reports are saved under the `audit/` folder as Markdown, human-readable and verifiable by third parties.

### Task A｜Daily Issue Triage Briefing (Runs daily)

Reads new issues and active discussions from the past 24 hours, and produces a structured breakdown:

- Confirmed bug reports (with reproducibility step status)
- Reports requiring additional information
- Duplicate or already resolved issues

### Task B｜Weekly PR Status Patrol (Runs every Monday)

Scans all open pull requests and flags three risk categories:

- PRs waiting for author response for more than 7 days
- PRs with passing CI but no reviews
- PRs modifying sensitive code paths

A copy-paste friendly follow-up comment draft is attached to each flagged item.

### Task C｜Cross-Issue Topic Clustering (Runs every two weeks)

Groups all open issues by recurring themes or shared root causes. It outputs a prioritized action list for maintainers.

## 📅 Execution Plan (4 weeks, verifiable milestones)

Each phase ends with a tangible, independently verifiable artifact instead of vague progress updates.

- **Week 1 — Minimum viable closed loop**
  Public repository + the first issue triage brief generated by Pokee inside `audit/`.
  The brief is marked: no manual edits.
- **Week 2–3 — Full workflow + quantitative measurements**
  Continuous runs for 14 days. Tasks A, B and C are all active.
  `RESULTS.md` records simple, honest metrics: estimated manual inspection time versus time spent reviewing Pokee outputs, plus the share of flagged items that the maintainer considers useful.
- **Week 4 — Feedback refinement + final polish**
  Deliver `POKEE_FEEDBACK.md`, documenting real-world observations on long-context association, periodic trigger stability, and instruction control for constrained output.
  Finalize the README so a new visitor can understand the project and locate results within 3 minutes.

## 📊 Value Loop

- Pokee → Project: Provides long-context reasoning power for recurring inspection tasks and produces publicly reproducible results.
- Project → Pokee: Delivers structured, actionable product feedback for the Pokee team, plus a reusable workflow template for other builders. If mature enough, this can serve as a reference implementation for GitHub maintenance workflows inside the Pokee ecosystem.

## ⚠️ Scope & Risk Control

- This is not a full-featured maintainer assistant. It is limited strictly to the three defined tasks, with clear inputs, outputs and validation rules. Narrow scope keeps the project deliverable and easy to evaluate.
- Perfection is not required. If Pokee produces unstable or incorrect results, those limitations are recorded truthfully in the report. Honest observations carry more weight than a polished demo with hidden flaws.
- Estimated total effort: 20–25 hours spread across four weeks, sized to finish within the Pokee review window and avoid scope creep.
