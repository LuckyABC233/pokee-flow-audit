# Pokee Flow Audit — Workflow Instruction

> This document contains the raw instructions executed by Pokee for periodic GitHub repository audits.
> Target repository: [Fill your repository URL here]
> Schedule: Daily / Every Monday / Every two weeks
> Output rule: Save results as independent timestamped Markdown files inside `audit/`. Preserve the original structured conclusion without cosmetic rephrasing.

## Global Rules (Shared by all tasks)

1. Only read issue, PR and comment content from the designated repository. Do not invent external information.
2. Output must be structured with clear categories. Link every finding to its original GitHub URL.
3. Explicitly mark ambiguous or undecidable entries. Never fabricate reproduction details.
4. Every generated report must start with this fixed header:

```plaintext
Generated by Pokee Flow Audit
Repo: {repo_url}
Run At: {time}
No manual edits.
```

5. Do not close issues, add labels or post comments automatically. Only produce comment drafts that the maintainer may copy and paste manually.

## Task A: Daily Issue Triage Briefing｜Schedule: Daily

Input: New issues from the last 24 hours + issues receiving new comments
Output file: `audit/issue-triage-YYYY-MM-DD.md`

Output structure:

1. One-sentence summary
2. 🐛 Confirmed / Reproducible Bug Reports
   - Issue link, title, reproducibility steps: complete / partial / missing
3. ❓ Need More Info
   - Issue link, title, what information is missing
4. 🔁 Duplicate / Already Resolved
   - Issue link, reference to the related original issue
5. 📌 Other (question, feature request, off-topic)

## Task B: Weekly PR Status Patrol｜Schedule: Every Monday

Input: All open pull requests
Output file: `audit/pr-audit-YYYY-MM-DD.md`

Output structure:

1. Summary
2. ⏳ Waiting author response > 7 days
   - PR link, title, copy-paste follow-up comment draft
3. ✅ CI Passed, No Review Yet
   - PR link, title
4. ⚠️ Sensitive Path Changes
   - PR link, brief description of changed files, risk note
5. General suggestion for the maintainer

> Comment drafts should be concise, friendly and follow standard open-source community tone.

## Task C: Cross-Issue Topic Clustering｜Schedule: Every two weeks

Input: All open issues
Output file: `audit/issue-cluster-YYYY-MM-DD.md`

Output structure:

1. Summary: total number of identified topic groups
2. Each topic group:
   - Topic name
   - List of linked issues with URLs
   - Extracted shared root cause
   - Maintainer recommendation: unify reply / track together / prioritize fix
3. Unclustered: isolated issues with no obvious connection

## Execution Constraints

- If there is no new repository activity in the cycle, still generate a report and state clearly: No new activity in this cycle.
- If the context is too long or ambiguous to confirm relationships, mark: Low confidence, need manual check.
- Do not guess author intent. All conclusions must be grounded in existing text.
